# Werewolf Arena 本地单人 Web 产品设计

**状态：已确认，Phase 3 已完成（Agent Runtime、自动推进与 API）**
**日期：2026-08-25**  
**仓库：`D:\AI\werewolf_arena`**

## 1. 产品目标与边界

### 1.1 首期目标

交付一个可在用户本机启动、通过浏览器游玩的单人狼人杀产品。每局由 1 名人类玩家和 5 名 AI 玩家组成。玩家能够创建或继续一局游戏，选择或随机获得身份，与 AI 进行多轮讨论和博弈，在死亡后以公开信息旁观者身份观看结局，并在结算后查看完整复盘。

产品首期追求的是“完整、可信、可读的单人对局体验”，而不只是离线规则演示。游戏系统必须是服务端权威：浏览器、模型和角色插件都不能绕过规则、读取未授权身份或直接修改对局状态。

### 1.2 首期范围

- 本地 Web：FastAPI 后端和 React + TypeScript 前端在同一台机器运行。
- 标准六人局：2 名狼人、1 名预言家、1 名女巫、2 名村民。
- 人类可随机身份或从本局允许的角色中指定身份；其余 5 个席位由 AI 填充。
- 人类行动不设时间限制。运行时在需要人类操作时暂停，直到收到合法提交。
- 白天支持 AI 陈述、人类不限时公开发言、AI 受控回应、由人类确认结束讨论后进入投票。
- 狼人玩家拥有只对狼阵营可见的夜间协商频道；其他角色的夜间技能按规则逐一处理。
- 浏览器只展示 AI 最终发言、最终公开行动和安全的简短行动说明，不展示模型原始思维链、私有 Prompt、私有记忆或其他身份秘密。
- SQLite 持久化房间、权威事件、快照、玩家会话、模型调用统计和战报；支持重启恢复、历史战报和结局复盘。
- 角色通过受信任的 Python 插件注册；引擎支持将来扩展人数、角色、阵营和规则组合。

### 1.3 不在首期范围

- 账号系统、公网部署、多人真人同局、匹配和好友系统。
- 支付、计费、云端配额或移动端 App。
- 允许管理员从网页上传并执行任意角色代码。
- 通用可视化规则编辑器；首期角色只能通过 Python 插件开发和发布。
- 展示任何模型隐式推理过程。

## 2. 用户体验与页面

### 2.1 视觉方向

前端采用“月夜秘仪”主题：深蓝与低饱和紫色构成夜晚基调，白天切换为暖灰和金色。页面使用克制的玻璃层次、月相和阶段过渡，不使用大面积霓虹、高频闪烁或会影响长文本阅读的动画。

主要布局为叙事/聊天视图：中央区域承载系统叙事和公开讨论，右侧区域展示人类私密身份卡、当前阶段、可执行行动、存活玩家及票型摘要。该布局优先保证玩家能看懂信息和自然输入，再逐步扩展为牌桌式皮肤。

### 2.2 页面与用户流

```text
首页
  ├─ 创建新对局
  │    ├─ 选择游戏模式（首期标准六人局）
  │    ├─ 选择身份或随机身份
  │    └─ 开始对局
  ├─ 继续未完成对局
  └─ 历史战报

对局页
  ├─ 公开叙事与聊天时间线
  ├─ 私密身份/技能/行动面板
  ├─ 存活玩家与票型摘要
  └─ 阶段状态与可操作按钮

结局页
  ├─ 胜负与身份揭晓
  ├─ 按权限解锁的完整事件复盘
  ├─ 角色和票型时间线
  └─ 再开一局或返回首页
```

### 2.3 视图权限

| 状态 | 人类可见内容 |
|---|---|
| 存活 | 所有公开事件、自己的身份与私有事件、自己被授权的角色能力。|
| 已死亡 | 之后的公开事件与阶段状态；不能看到存活者身份、狼人私聊、查验结果、药物或其他私有事件。|
| 结局 | 完整身份、全部事件、AI 最终行动结果与统计；仍不展示模型原始思维链或原始私有 Prompt。|

## 3. 一局游戏的交互规则

### 3.1 房间与身份

创建房间时，服务端根据 `GameMode` 校验角色配额、玩家数和阵营平衡。玩家可以选择一个当前模式允许的角色，或选择随机；服务端再为剩余 5 个 AI 席位分配符合配额的角色。真实角色仅保存在服务端权威状态中。

### 3.2 夜晚

夜晚按模式定义的优先级顺序执行。标准局的默认顺序为：狼人协商和袭击意图、预言家查验、女巫救人或毒人、环境结算和公开夜间公告。

- 人类是狼人时，先进入私密狼队频道，与狼人 AI 进行有限轮次协商，再由人类提交最终目标。
- 人类持有夜间能力时，运行时显示合法目标和能力说明，并无限等待其提交。
- 人类不具备当前夜间能力时，前端显示安全阶段状态，服务端驱动相应 AI。
- 任何角色私密事件都不通过公共 WebSocket 流发送。

### 3.3 白天讨论与投票

1. 服务端发布公开夜间公告。
2. 所有存活 AI 按随机座位顺序进行第一轮公开陈述。
3. 人类可不限时发送公开发言；每次人类发言后，由调度器选择相关 AI 进行一轮受控回应。
4. 人类点击“结束讨论，进入投票”后，讨论阶段关闭。
5. AI 以随机座位顺序公开投票；随后人类提交投票或弃权。
6. 裁判计算唯一最高票或平票，写入权威事件并推进到下一夜或结局。

讨论轮次、单条发言长度、AI 回复次数、模型 Token 和费用均受游戏模式与预算策略约束；人类等待时间不计入模型预算。

### 3.4 AI 对外展示

每个 AI 只能向对局页面暴露最终结构化结果：公开发言、公开投票、公开技能结果以及不含私密信息的简短行动说明。前端可显示“AI 正在行动”状态，但不能显示 token 流、系统 Prompt、推理草稿或未通过规则校验的模型输出。

## 4. 技术架构

### 4.1 分层

```text
React + TypeScript
  └─ UI、路由、授权视图、WebSocket 客户端
         ⇅ REST / WebSocket
FastAPI Application
  ├─ 房间 API、会话 API、事件订阅 API
  ├─ View Projection：按访问者和阶段过滤数据
  ├─ Game Runtime：每房间串行推进和暂停/恢复
  ├─ Domain：规则、状态、事件、模式、角色插件
  ├─ Agent Runtime：记忆、Prompt、模型调用、预算和降级
  └─ Repository Interfaces
         ⇅
SQLite（首期）→ PostgreSQL / Redis / Object Storage（未来）
```

### 4.2 服务端权威与事件流

游戏领域只接受结构化 `Command` 或 `Action`，只产生权威 `GameEvent`。浏览器、AI 策略和插件不直接改变 `GameState`。FastAPI 在调用领域前完成会话、房间归属和基础输入验证；领域再验证阶段、角色、目标、次数、资源和冲突。

每个房间由一个 `GameRuntime` 串行处理命令。它将人类操作、AI 决策和阶段推进排入同一队列，因此不会出现并发投票、重复扣药或重复结算。运行时在需要人类行动时持久化快照并进入等待状态；收到合法命令后继续。

### 4.3 API 与实时事件原则

- REST 负责创建/查询房间、恢复历史、提交确定性命令和加载首屏。
- WebSocket 负责阶段变化、公开发言、投票、合法的私密提示和结局通知。
- WebSocket 事件携带单调递增序号；客户端重连提供最后序号，服务端补发该会话有权限看到的遗漏事件。
- 所有响应均来自 `ViewProjection`，而不是序列化完整领域状态。

## 5. 规则、模式与角色插件

### 5.1 通用模式

`GameMode` 定义玩家数、角色配额、阵营配额、昼夜阶段顺序、讨论和投票规则、死亡公开规则、行动预算和版本。标准六人局只是一个内置模式实例，不是引擎常量。

创建房间前必须验证：席位数与角色数一致、阵营/角色配额自洽、所有引用插件可用、胜负条件可判定、阶段顺序不存在无法结束的循环。

### 5.2 插件契约

每个受信任 Python `RolePlugin` 在服务启动时注册，并提供：

- `RoleDefinition`：角色 ID、名称、阵营、展示文案、版本；
- `AbilityDefinition`：可用阶段、次数、合法目标、输入 Schema 和公开结果策略；
- 事件钩子：接收授权事件上下文并提出结构化效果；
- 私有状态定义：仅服务端及被授权角色可读取的资源；
- `PromptProfile`：面向对应 AI 的身份目标、行为边界和私有信息模板。

插件不可直接写全局状态。它只能返回 `Action` 或 `EffectProposal`；裁判内核统一验证和应用效果，随后生成权威事件并更新可见性投影。首期插件为狼人、预言家、女巫、村民。新增守卫、猎人或第三方阵营角色不得修改 HTTP API 或主状态机。

每个房间、快照和报告记录 `game_mode_version` 与 `role_plugin_version`。旧局复盘需要对应版本的插件可用；不兼容升级必须以新版本注册，而不是就地覆写旧规则。

## 6. Agent Runtime 与模型

### 6.1 模型接入

模型适配层默认兼容 OpenAI Chat Completions。Endpoint、模型名和 API Key 仅从服务端 `.env` 读取。该接口应允许未来给不同 AI 设置不同模型、温度、Token 预算和 Prompt 版本，但首期可采用统一提供商与统一预算。

### 6.2 信息与记忆

每个 AI 只接收其 `PlayerObservation`：公共事件、自己角色、合法能力、自己的私有事件和被规则明确授权的信息。狼人可看到仍存活的狼人队友和私密协商；预言家只看到自己的查验；女巫只在授权窗口看到相关信息。

每轮结束后，运行时更新该 AI 的私有记忆摘要，至少保留：已知事实、公开承诺、怀疑对象、投票记录、查验/药物等私有资源和未完成目标。旧聊天文本被摘要压缩并保留可追溯事件编号，防止上下文无限增长。

### 6.3 失败与成本控制

- 每次模型调用设置超时、一次受控重试和指数退避。
- 输出必须满足 JSON Schema；第一次解析失败时只进行一次格式修复请求。
- 仍失败时执行该阶段合法的安全降级行动，例如 `noop`、弃权或不使用技能，并记录失败事件。
- 对局级别限制调用次数、输入/输出 Token 和费用；达到上限后停止继续调用模型并应用安全降级，不使房间卡死。
- 原始模型响应、完整 Prompt 和密钥不写入用户战报或浏览器日志。

## 7. 数据、隐私与恢复

### 7.1 持久化模型

| 表/实体 | 内容 |
|---|---|
| `rooms` | 房间元信息、模式版本、当前阶段、状态和创建时间。|
| `participants` | 席位、玩家类别、人类会话引用、存活状态和服务端角色引用。|
| `game_events` | 追加式权威事件、序号、可见性范围和事件数据。|
| `game_snapshots` | 完整状态快照及最后事件序号，用于恢复。|
| `player_sessions` | 本地会话令牌、所属房间与访问权限。|
| `agent_runs` | 模型/Prompt 版本、调用统计、延迟、Token、成本与失败原因。|
| `reports` | 结局摘要、公开战报和完整复盘索引。|

### 7.2 恢复与删除

关键阶段结算后写入快照。服务重启时，从最近快照和后续权威事件恢复状态，绝不重新调用已完成的 AI 决策。首页显示可继续房间和历史战报；用户可以删除房间及其关联事件、快照和报告。

### 7.3 本地安全基线

首期不做账号系统，但必须使用随机本地会话令牌、严格房间归属校验和本地 CORS 配置。完整快照、私密事件和模型密钥只由服务端访问。错误日志和战报必须脱敏；公共发言需要长度限制和基础内容安全检查。

## 8. 测试与验收

### 8.1 自动化测试

- 领域单元测试：胜负、阶段转换、行动合法性、插件契约、技能冲突、版本校验。
- 隐私测试：不同角色、死亡旁观者和结局复盘的投影均不泄露未授权字段。
- 运行时测试：人类等待、AI 行动、超时降级、预算耗尽、重复命令与断点恢复。
- API/数据库测试：创建房间、选择身份、重连补事件、删除对局、旧局读取。
- 前端端到端测试：创建、发言、投票、死亡旁观、恢复、结局复盘和隐私断言。
- 真实模型 smoke test：默认不运行；独立配置后记录成本、延迟和失败率。

### 8.2 首期验收标准

1. 用户可在本机启动服务并从浏览器创建标准六人局。
2. 用户可选择或随机身份，并和 5 名 AI 完整玩到胜负或平局。
3. 人类操作可无限等待；重启服务后可继续未完成对局。
4. 任何浏览器响应、WebSocket 消息或公开战报均不泄露其他存活玩家的私密信息。
5. 人类死亡后仅能旁观公开信息，结局后可查看完整复盘。
6. 模型异常、非法输出或成本上限不会导致房间崩溃或突破规则。
7. 新角色可以用符合契约的 Python 插件注册，标准局不依赖将角色写死在引擎中。

## 9. 实施顺序

1. 初始化单仓库、开发环境、领域模型、数据库迁移和角色插件契约。
2. 迁移并重构标准六人局规则，完成模式配置、权威事件、可见性投影和房间运行时。
3. 实现 SQLite Repository、快照/恢复、会话和 FastAPI REST/WebSocket 接口。
4. 实现 Agent Runtime、OpenAI 兼容适配器、私有记忆、狼人协商、预算和失败降级。
5. 实现 React 月夜秘仪界面：首页、创建/继续、对局、结局和复盘。
6. 补齐测试、真实模型 smoke test、本地启动文档和故障排查说明。

后续版本依次增加账号和公网部署、多真人房间、PostgreSQL/Redis、后台受限规则配置、锦标赛评测及模型/Prompt 对比。
